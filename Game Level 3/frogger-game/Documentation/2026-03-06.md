Para esto, vamos a usar las constantes de Grid que teníamos como base, para medir el tamaño de movimiento, como lo calculamos el primer día, ya tendríamos nuestros valores:


Por otro lado, decidí preguntar y solicitar una recomendación acerca de mi manejo de playable area, mi idea era dejarlo en un singleton o Resource Component que se pudiera exportar, para manejar los archivos, la recomendación... hacer el singleton de **GameStats**, dónde se maneja mejor el sistema de carga y modificación de la puntuación.

Después de hacer los chequeos de código, nos dimos cuenta que de nuevo, la IA no es del todo confiable, y que estaba agarrando el viewport size (con sus reemplazos), y no estaba utilizando los valores base (que son los esperados), en dicho caso, toca modificar esa parte del código.

Al final, sabemos que debemos de utilizar siempre el **visible_rect** en vez del viewport.get_size(), es preferible el viewport.get_visible_rect(), así a la hora de hacer escala, va a funcionar de forma correcta.

Recordatorio: Usar el
```
viewport = get_viewport()
area_of_game = viewport.get_visible_rect()
```    
En vez del viewport.get_size(), ésto en caso de por ejemplo, desear incrementar en las distintas pruebas a distintas resoluciones el arte o el juego, debemos de probar que funcione en el área del juego, si se usan valores de `viewport.get_size()`, va a agarrar incluso los valores de reemplazo.
De igual manera, siempre es mejor usar el modo de compatibilidad a la hora de debuggear

También preguntamos acerca de cómo deberíamos controlar el manejo de singletons usados, según lo observado, es mejor crear **singletons** únicamente cuando éstos tienen una función específica, en el caso de un Frogger, es un juego simple, quizás solo ocupe un solo singleton (GameStats), pero para una estructura más grande tendríamos:

* GameStats: (Puntuación, Datos como Resolution, Playable Area, Core Game Data, Vidas, etc)
* AudioManager: (Efectos de Sonido, Música, Controlador de Sonido, etc)
* SaveManager: (Funcionalidad de Guardar/Cargar Partidas)
* InputManager: (Si esperamos por inputs específicos o un manejo de input custom)
* UIManager: (Si controlamos actualizaciones inmediatas de UI y transiciones)
